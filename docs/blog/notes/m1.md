# M1 notes

Raw material for blog post 1. Facts only.

## Task 1: the fixed-step clock (2026-11-20)

- Platform code moved from `src/core/` to `src/platform/`, with `windows/` and
  `linux/` subdirectories. Each platform `.cpp` is still wrapped in
  `#if VESPERA_PLATFORM == ...`, so the move needed no CMake change.
- `core::FixedStep(step_secs, max_steps_per_advance = 8)` banks elapsed time and
  returns how many simulation steps are due. `alpha()` is the leftover fraction of
  a step, for blending between the last two states when rendering.
- **Stall cap.** A 10 s stall (debugger break, window drag) runs 8 steps, not
  1000. When the cap is hit the bank is emptied. Keeping the remainder instead
  would save less than one step, which nobody sees after a stall.
- `elapsed_seconds` must not be negative (asserted): a steady clock never runs
  backwards, so a negative value is a caller bug.
- Dropped from the plan: a `step_secs()` getter. Its only caller would have been
  the main loop, which already has the step as a constant.
- The step rate (`1.0 / 120.0`) is a placeholder. The simulation rate is separate
  from the display rate, because rendering blends with `alpha()`. Head tracking
  bypasses the simulation. The real rate gets chosen in M3, once there's
  gameplay to measure.

## CI: the Windows lane went red without a code change (2026-11-20)

- The lane failed with `STL1000: Unexpected compiler version, expected Clang 22
  or newer.`, the same error M0 fixed by pinning `runs-on: windows-2025`.
- **Cause:** GitHub is moving the `windows-2025` label to the
  `windows-2025-vs2026` image. During the rollout a job gets either image, so
  the lane passed or failed depending on which one it drew. The job's "Set up
  job" log names the image.
  - The VS 2026 image defaults to MSVC 14.52, whose STL refuses Clang older
    than 22.
  - The runner's `clang-cl` is LLVM 20.1.8 (`C:\Program Files\LLVM`).
- **Fix:** `vcvars64.bat -vcvars_ver=14.44` selects the VS 2022 toolset (MSVC
  14.44), which accepts Clang 19 and newer. Both images install it. If 14.44 is
  missing, the step now fails with a clear message instead of failing later at
  configure time. The pin can go once the runner's LLVM is 22 or newer.
- Lesson: a versioned runner label is not a fixed image. Pin the toolchain you
  depend on, not the label.
- A detour: the log checked after the fix was a manual re-run of the commit
  before it, and still red. Check the commit SHA in a log before reading it.

## CI: lane times (2026-11-23)

- Windows takes about 4 min, the Linux lanes about 1 min. Both runners have 4
  cores.
- Before the build starts, Windows spends about 77 s against about 30 s on
  Linux. Configure alone is 35 s against 7–10 s: CMake's compiler checks start
  many short processes, and process creation is slow on Windows.
- Removed `choco install ninja` from the Windows lane, saving about 12 s. It did
  nothing ("ninja v1.13.2 already installed"), and Visual Studio puts its own
  ninja on PATH as well.
- Not done yet: caching compiled objects between runs (sccache/ccache). Revisit
  if build time starts to hurt.
